## 1. Configuración local

El repositorio ya usa `main` como rama de entrega. Git Flow se inicializó con las convenciones por defecto y con `main` como rama de producción. No se reescribió el historial.

| Rama o prefijo | Uso |
|---|---|
| `main` | Entrega que ve el docente |
| `develop` | Integración del equipo. Nace desde `main` |
| `feature/` | Una historia, por ejemplo `feature/US-008` |
| `release/` | Cierre de una versión |
| `hotfix/` | Corrección sobre `main` |
| `bugfix/` | Corrección sobre `develop` |
| `support/` | Soporte de una versión anterior |

Comando usado:

```text
git flow init -d
```

`develop` queda publicada en `origin` junto con `main`. Las dos apuntan al cierre de esta inspección.

## 2. Secuencia de la próxima historia

```text
git checkout develop
git pull origin develop
git flow feature start US-008
```

El trabajo se commitea en `feature/US-008`. Al terminar las pruebas:

```text
git flow feature finish US-008
git push origin develop
```

El cierre de una versión, cuando el sprint esté aceptado:

```text
git flow release start v1.2.0
git flow release finish v1.2.0
git push origin main
git push origin develop
```

## 3. Lo que no se hace

No se hace push de una historia directo a `main`. No se usa `push --force` sobre `main` ni sobre `develop`. No se reescribe el historial que ya está publicado.
